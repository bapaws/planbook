# 冷启动与首页卡顿优化计划

日期：2026-10-17  
状态：已实施首批无 schema 变更优化；2026-10-18 获授权继续优化提醒重排与启动强制同步，实施结果见末尾记录。首页订阅和业务数据库结构继续保持不变。  
范围：沿用原问题编号，规划第 1、2、3、5、6、7、8、9、10 项。

## 约束与判断依据

- 用户已反馈：冷启动卡顿，重复任务较多；具体机型、系统、数据量和退出日志尚缺。
- **第 4 项「首页订阅数量」暂缓**：不合并各标签、空白拖放区、侧栏的任务订阅，不迁移这些 BLoC 的职责，不改变筛选、拖拽、分组和展开逻辑。
- 当前代码已包含重复规则同步、实例缓存刷新及其回归测试修复。以下方案以这些修复为基线，实施前重新核对，不覆盖或撤销。
- 下文的「原因」是源码中已确认的执行行为；对该用户十秒等待、闪退的贡献尚未通过真机测量证实。
- Flutter UI isolate 卡顿、Android 主线程阻塞、异步加载等待、进程退出需分别度量，不能凭十秒这个时长认定为数据库锁超时或 ANR。
- 各项独立确认、独立交付。新增服务统一在 `lib/bootstrap.dart` 注册，沿用现有 Repository 与 BLoC 边界。

## 0. 先建立可比较的基线

### 记录什么

为启动各阶段记录开始、结束和失败，使用统一的启动编号关联：

1. SDK 与本地配置初始化完成。
2. 数据库完整性检查开始与结束。
3. 首页第一帧、第一份本地任务结果、首份列表实际绘制完成。
4. 重复实例生成：进入次数、实际执行次数、命中缓存次数、计算与写入耗时、生成数量。
5. 提醒：实际取消/预约次数、已有预约数、重复请求合并次数、队列等待及执行时间。
6. 云同步：普通/强制触发原因、下载数量、合并写库耗时、提醒副作用耗时。
7. 小组件：刷新批次、安装实例数、快照次数与字节数、查询和绘图耗时。
8. Flutter UI/raster 帧时间、Android 主线程跟踪、内存峰值及进程退出原因。

只记录阶段、计数和必要的匿名标识；不输出任务正文。分段测量不能将重叠异步任务的耗时直接相加为启动总耗时。

### 怎么比较

- 性能分析用 profile 构建；最终启动与稳定性用相同渠道的 release 包复核。debug 结果仅供定位。
- 使用相同版本基线数据，覆盖小数据、重复任务多、历史实例多、WAL 较大四类情况；合成数据只能辅助归因。
- 分开测试有/无桌面小组件、在线/断网、正常缓存/首次升级、冷启动/后台返回。
- 每个关键对照至少进行 10 次进程冷启动，记录中位数、最慢一次和设备状态；不要把进程冷启动等同于清空文件系统缓存。
- 同一时刻只切换一个待验证路径。诊断包可临时跳过提醒重排或小组件刷新做对照，正式方案不能以关闭功能作为优化结果。
- 退出问题收集 logcat、系统退出原因和可用的 ANR/原生崩溃记录；没有记录时标为待确认。

产出：一份实际测量基线、各阶段耗时分解、各项优化前后对比。当前不承诺优化到固定秒数。

## 1. 提醒调度：稳定 ID、精确取消和请求合并

### 原因与代码位置

- `packages/planbook_repository/lib/task/alarm_notification_service.dart`：`cancelForTask()` 固定遍历 50 个实例与 20 个提醒，每个任务发起 1,000 次取消。
- `_notificationId()` 使用 `Object.hash()`，不保证跨启动一致；按 occurrence 下标标识预约也不能稳定表示某个实际日期。
- `lib/root/home/view/root_home_page.dart`、`lib/app/view/app.dart`、`TasksRepository.syncTasks()` 均可能触发重排。同一任务的取消与预约缺少统一顺序。
- `_initialize()` 只有完成标志，多个调用在首次初始化结束前可重复进入。
- 当前通知没有携带任务归属 payload，旧 ID 无法仅靠当前公式准确反推。

### 修改方案

1. **建立本地预约账本**：记录用户、任务、实例实际日期、规范化提醒配置、整数通知 ID、内容指纹、执行状态与版本。它是本设备调度状态，不进入云同步 Outbox。
2. **使用稳定的业务键**：由用户 ID、任务 ID、实际实例日期与提醒配置构成。持久化分配通知 ID；若采用稳定摘要转整数，必须处理整数碰撞，不能只换一个 hash 函数。
3. **差量执行**：计算期望预约集合，与账本及系统 pending 列表对照。取消已移除项，增加缺失项，更新内容或时间变化项；一致项跳过。一次批次读取系统 pending 列表，避免逐任务反复读取。
4. **统一调度入口**：同任务的取消、修改、预约按顺序执行。相同版本的重排可合并；新版本修改不能简单丢弃，完成后继续处理最新状态。删除/注销使旧版本任务失效，防止旧请求重新预约。
5. **共享初始化 Future**：并发调用等待同一次初始化；失败后允许重试。统一处理 fire-and-forget 的错误，保存可重试状态。
6. **准确保存成功与失败**：只有原生预约成功后才标为已预约；进程在原生操作与账本提交之间退出，下次通过 pending 列表与带版本的 payload 校正。
7. **保留现有窗口与业务口径**：第一版仍按现有未来 60 天、最多 50 个 occurrence 计算；暂不同时改变预约上限、提前提醒规则或单次完成/删除的取消范围。

### 旧版本迁移

- 新账本无法识别全部旧随机 ID，必须有一次迁移，不能只发布新 ID 算法。
- 先核查应用内所有预约来源。若全部属于此任务提醒服务，可以在持久化迁移状态下执行一次「清理待触发预约→从本地有效任务重建」。使用待触发预约清理接口，避免无意清除已经展示的通知。
- 重建任务集须同时覆盖单次与重复任务，不能只调用现有「重复任务重排」入口。
- 若另有预约来源，先定义归属与各来源重建能力，不能按标题猜测归属或直接清空。
- 迁移期间串行处理调度；中断后恢复；全部成功或已明确保存重试项后再完成迁移。明确评估清理到重建之间的提醒空窗。
- 首版保留当前单次实例处理语义；已完成/已删除实例的提醒行为若需修正，另立业务修复项并确认。

### 验证与验收

- 多次独立进程启动，同一业务预约对应相同 ID；预约总量不因重复启动累积。
- 实际预约 3 条时只取消相关的 3 条，不再固定调用 1,000 次；账本缺失时能从系统状态恢复。
- 覆盖编辑时间/标题/提醒、移除提醒、删除、完成/撤销、重复规则结束、时区变化、用户切换。
- 覆盖启动重排与同步重排并发、删除与旧预约并发、原生接口失败、迁移中途退出。
- 单元测试验证差量与队列；Android/iOS 真机验证通知触发、权限拒绝与升级迁移。

收益预期高；兼容风险较高，主要在旧预约迁移及并发顺序。建议作为一个完整兼容单元交付，不能只替换 ID 后上线。

## 2. Android 桌面小组件：后台更新与减少快照

### 原因与代码位置

- `android/app/src/main/kotlin/com/bapaws/planbook/widget/TimeBlockWidgetProvider.kt`、`WeekWidgetProvider.kt`：更新入口通过 `runBlocking(Dispatchers.IO)` 等待查询；调用线程仍被阻塞。
- `WidgetDatabase.kt`：每次 `open()` 都复制主数据库、WAL、SHM，查询后再删除快照。同一批组件可能重复复制。
- 时间块组件为 Launcher 提供的多个尺寸生成 Bitmap，增加绘图时间与内存峰值。
- `AppHomeWidget.syncPremium()` 每次写入会员状态后刷新时间块组件，即使有效会员状态没有变化。
- 对当前冷启动的影响有条件：用户安装时间块组件时，启动期间的会员刷新可触发这条重路径。未安装时不会执行对应实例的读库绘图。

### 修改方案

**第一步：改变执行方式，保留当前数据与布局。**

1. 更新广播使用 `goAsync()` 配合有界后台执行器处理短任务，在 `finally` 释放 PendingResult；可能超过广播期限的工作使用合适的后台任务机制，不能无限挂起。
2. 把数据库复制、查询、Bitmap 绘制全部移出 Android 主线程，而非仅把 SQL 包在 IO dispatcher 中。
3. 按组件 ID 合并刷新，限制并发；新一批数据到来后旧批次不能覆盖新结果。
4. 只更新已安装的组件；会员值相同且没有其他刷新理由时，跳过由会员刷新发起的重复更新。
5. 会员状态去重不能阻止任务、日期、主题等其他原因的更新。

**第二步：减少复制量，另行验证一致性。**

1. 同批同用户更新复用一个经过一致性处理的快照，批次完成后释放，避免每个组件各复制一次。
2. 逐步采用由 Flutter 数据源提供的最小组件数据，或通过 SQLite 支持的备份方式生成一致性快照；评估组件在 App 未运行时的读取与降级路径。
3. 首步不恢复 Android SQLite 与 Flutter sqlite3 对活跃 WAL 主库的并行访问，也不以「直接读正在写的数据库」换取速度。
4. 为候选尺寸设合理的像素与总内存预算，保留实际布局需求；避免仅在绘图结束后回收就宣称解决峰值问题。

### 验证与验收

- 更新期间 Android 主线程不再等待全库复制和绘图；记录后台总耗时，确认不是只把开销隐藏。
- 覆盖无组件、单组件、多组件、不同尺寸、非会员/会员、系统刷新、App 未运行、点击完成后刷新。
- 覆盖 App 同步写库与组件读取并发、用户切换、刷新失败和连续快速更新。
- 同批复制次数减少，结果与原组件一致；内存峰值有测量证据。

收益有条件但可能很高。线程调整与快照数据通道拆成两次交付，避免同时改线程、存储与布局。

## 3. 重复任务实例：生成去重、覆盖范围与计算调度

### 原因与代码位置

- `database_task_today_api.dart` 中计数与列表入口分别调用 `preGenerateTaskOccurrences()`。
- `database_task_api.dart` 用「当天有没有实例」筛任务。当天本来不重复、或该实例已有软删除标记时，仍可能重新计算已经覆盖的未来范围。
- 当前已使用事务保护实例生成与规则同步，但事务不会消除重复计算，也不会自动把 Dart 日期计算移到后台 isolate。

### 修改方案

1. 保持所有首页订阅入口不变，在其下方的生成层统一协调。
2. 以数据库实例、用户和日期范围合并进行中的生成请求；不同 API 对象必须共享同一协调器，不能各自有一份去重锁。
3. 记录「指定任务版本已计算过的日期区间」，包含生成结果为空的区间；不能只记录有没有实体，也不能只用最大日期代表所有中间日期都覆盖。
4. 用规则、时间、父子/分离状态、删除状态等生成版本区分缓存。规则变化使旧版本覆盖记录失效。
5. 实例写入与覆盖记录原子提交，失败不标记覆盖成功。保留软删除占位和分离实例压制逻辑。
6. 第一版保留未来三个月范围。先减少冗余计算；实际仍有 UI 阻塞时，再把纯日期计算移入工作 isolate，并测量对象传输成本。
7. 若计算移出事务，读取任务版本后在提交事务中重新核验版本，过期计算结果丢弃重算，不能破坏当前「同步与生成互斥」的正确性。
8. 分批构造/提交需保证覆盖状态与实例一致。历史/未来日期仍按需补齐，不把固定延迟作为唯一正确性保证。

### 验证与验收

- 多个查询同时请求同一范围，只实际生成一次；每周一任务在周二反复查询时不重复生成完整窗口。
- 覆盖空结果、次数上限、结束日期、跨月、跨年、时区/夏令时、子任务、已分离或软删除实例。
- 保留并通过当前未提交的重复规则同步、缓存刷新、分离实例日期查询回归测试。
- 实例集合与原业务规则一致；首屏 UI 阻塞和重复写入下降。

收益预期高；风险在缓存失效与并发提交，先做去重，再评估计算迁移。

用户已明确暂不修改。第 3、5 项仅优化现有订阅下方的计算与查询；第 10 项仅调整状态处理，均不合并或删除首页数据订阅。

## 5. 数据库读取：批量标签查询与经过验证的索引

### 原因与代码位置

- `DatabaseTaskApi.buildTaskEntities()` 对每个任务依次等待 `getTagEntitiesByTaskId()`；后者再查标签及父标签，形成随任务数增加的查询链。
- 本地 Drift schema 未定义这些业务查询的显式辅助索引；已有主键以及 `(taskId, occurrenceAt)` 唯一索引，不应重复创建。
- `supabase.sql` 的索引属于远端 PostgreSQL，不会使本地 SQLite 自动获得同样的索引。SQLite 也可能临时使用自动索引，因此不能未经查询计划就把每条查询称为全表扫描。

### 修改方案

1. 在一次实体组装中先收集唯一任务 ID，批量取关联标签，构建 ID 映射；按数据库参数限制分批，避免超大 IN 子句。
2. 批量加载所需标签与父链，保持当前用户、软删除、`linkedTagId`、标签排序及循环保护语义。
3. 第一版缓存仅限本次组装，避免增加长期缓存失效问题；保留当前任务、实例、完成状态、子任务的组装与去重口径。
4. 对实际生成 SQL 执行 `EXPLAIN QUERY PLAN`，结合大数据耗时决定索引。优先候选：有效 `task_activities(task_id, occurrence_at)`、`task_tags(task_id, user_id)`、`tasks(parent_id)`，以及逾期查询可能需要的日期方向索引。
5. 现有任务优先的唯一索引能服务部分实例查询，是否另加日期优先索引取决于查询计划；不预先一次性加满所有候选。
6. 必要时检查子任务 JOIN 的结果行放大，但把 SQL 重写作为下一步，先完成批量标签读取和索引，以减少业务语义变化。

### 迁移与验证

- 用 Drift schema 声明和迁移管理索引，新安装与旧库升级都生效；schema 当前为 3，实施时按实际合并次序确定新版本。
- 验证索引创建耗时和库体积，单列查询性能改善不能抵消不可接受的首次升级卡顿。
- 测试多标签、父标签、循环数据、同一任务多个实例、不同用户和子任务。逐项对比结果与排序。
- 单次组装的标签查询数由逐任务增长改为少量分批查询；完整首页订阅数量保持不变。

收益预期中到高；先批量读取，再独立交付索引迁移。

## 6. 启动同步：先保证增量正确，再减少全量工作

### 原因与代码位置

- `AppBloc._onUserProfileRequested()` 的初次用户事件也会走 `force: true`，包含任务、关联标签、活动以及笔记数据。
- Supabase API 已有 3 秒节流，但它返回空列表，不能让多个调用方等待同一次合并完成；也不能作为完整的同步并发管理。
- `TasksRepository.syncTasks()`、`NotesRepository.syncNotes()` 逐记录检查 Outbox、解析并写入。
- 当前工作区强制同步还承担「修复已缓存的旧规则实例」职责，不能直接删掉强制刷新。

### 实施前必须确认的正确性条件

1. **按用户保存游标**：当前任务/笔记游标 key 未包含用户 ID；先设计按用户迁移，不能让新账号继承旧账号的游标。无法证明旧游标归属时，该账号进行一次基线同步。
2. **关联表变更可见**：目前增量过滤主要依据主表时间。需核实活动新增/删除、任务标签变更、笔记标签变更是否更新主表游标，或是否有独立的关联增量机制。仓库 schema 不能证明生产环境已具备完整触发器。
3. **提交后推进游标**：当前 API 获取结果后即保存游标，本地合并随后才进行。方案需改成拉取返回待提交游标，只有本地合并成功后才确认；中断允许重放，不能跳过未落库结果。
4. **处理分页与并发边界**：完整排序和稳定分页、相同时间戳记录、同步期间新增更新均需有明确策略；不以单次结果等同于服务端全部记录。
5. **保留待上传修改**：继续以本地 Outbox 保护尚未上传的记录。账号切换后旧请求不得写入新账号的游标或调度状态。

### 修改方案

- 先加入按用户/资源的进行中请求复用；force 请求遇到进行中的增量同步时，等待后执行必要的强制任务，不能静默吞掉。
- 将旧实例修复做成可重复、按版本记录完成状态的专项维护步骤；其覆盖对象和失败重试独立验证后，才让正常启动不再承担每次全量修复。
- 正常已完成基线的账号用增量；首次登录、换号、恢复损坏库、修复版本升级和显式强制刷新保留全量能力。
- 分批查询待同步 ID，合并相同标签写入；根据测量决定写库分批。每批保证父子/关联一致性，整个拉取结果成功落库前不推进总游标。
- 未变化数据避免重复写入；只有会影响提醒的变化进入第 1 项调度队列。
- 沿用当前本地数据展示流程，将非首屏维护错峰执行，但不改第 4 项的订阅结构，也不延误用户主动刷新。

### 验证与验收

- 双设备新增、修改、完成/撤销、删除、关联标签变化都能通过增量同步到达。
- 覆盖大结果分页、相同时间戳、弱网、写库失败、进程中断、重试、Outbox 冲突和账号切换。
- 已有旧实例修复仍生效；手动强制刷新确实执行。
- 对稳定账号的后续冷启动减少下载与写入，且数据结果和提醒结果正确。

收益可能高，但数据一致性风险最高。若关联增量条件尚不具备，先优化请求复用和批量处理，保留全量兜底。

## 7. 历史逾期统计：先优化查询，延迟策略单独确认

### 原因与代码位置

`RootTaskBloc._onCountRequested()` 启动同时订阅收集箱、今日和逾期计数。`DatabaseTaskOverdueApi.getOverdueTaskCount()` 关联历史实例与完成记录，数据量可能随长期使用增加。

### 修改方案

1. 第一版保持三个计数订阅和徽标行为不变，先采用第 5 项验证有效的索引，测量实际收益。
2. 必要的 SQL 调整需逐条验证非重复任务、分离实例、重复实例、完成记录的计数口径，不能顺带改变 count 的含义。
3. 如果仍明显影响首屏，可提议在首次今日列表绘制后启动逾期统计。由于这改变订阅启动时机，与用户暂缓第 4 项的边界相邻，**需额外单独确认**，默认不纳入第一版。
4. 聚合缓存仅在测量证明必要后设计，必须处理跨日、任务/活动变化、规则变更、换号及失败重算；不能直接把缓存当真实计数。
5. 不通过删除历史实例、隐藏旧逾期任务或缩短统计日期范围来提速。

### 验证与验收

长时间未完成的每日重复任务、大量完成记录、改期分离实例等场景计数与基线一致。先观察查询耗时与数据库队列等待，再决定是否需要时机调整或统计缓存。

第一步风险较低；时机调整和聚合缓存风险较高，拆开确认。

## 8. 数据库完整性检查：先移线程，再评估检查频率

### 原因与代码位置

`bootstrap._initApp()` 在挂载主 App 前等待 `AppDatabase.recoverCorruptIfNeeded()`；其 `_quickCheckOk()` 同步调用 SQLite `PRAGMA quick_check`，发生在 UI isolate。普通 Drift 连接使用后台 isolate，并不能覆盖这条单独打开 SQLite 的路径。

### 修改方案

1. 首版仍在打开业务数据库之前完成检查，把路径解析保留在可访问插件的上下文中，将打开/检查/关闭 SQLite 的工作放进独立 isolate。
2. 明确工作 isolate 的 SQLite 动态库初始化与临时目录配置，不能依赖主 isolate 的全局设置自动传递。
3. 检查结果结构化：正常、确认损坏、暂不可用/锁定、其他失败；不能把超时或 busy 视为损坏。
4. 不能给同步 FFI 查询简单套 `Future.timeout` 后就继续删文件或打开第二条业务路径；必须确认检查连接已关闭且没有后台任务继续操作文件。
5. 第一版保留检查时序、先恢复后开库。这样主要消除画面冻结，总等待未必同幅度下降。
6. 后续根据测量再决定降低检查频率或改成异常触发，并保留首次打开失败的恢复路径，单独确认。
7. 对原恢复策略先补验证：隔离主库、WAL、SHM 时保留可恢复材料，避免误删包含未同步数据的文件；所有恢复动作互斥完成。

### 验证与验收

- 大库检查时占位页仍可绘制；检查连接与正式连接不发生恢复操作竞争。
- 覆盖正常库、损坏库、无法打开、busy/locked、恢复中断，以及包含未同步 Outbox 的数据。
- 分别报告 UI 阻塞改善和总检查耗时；检查频率没有确认前不改。

收益取决于实际库体积；线程迁移风险中等，恢复策略与检查频率变更拆开交付。

## 9. 初始化与主题：控制重复订阅和根节点计算

### 原因与代码位置

- `bootstrap.dart` 派发 `AppInitialized`，首页标签加载结束后又派发一次。
- `AppBloc._onInitialized()` 每次派发背景和象限配置请求，它们通过长期 `emit.forEach()` 监听，未配置替换旧监听的并发策略。
- `App.build()` 监听整个 `AppState`；`getTheme()` 多次重新计算种子配色和 `ThemeData`，即使变化来自用户资料或版本检查。

### 修改方案

1. 区分一次性初始化与显式重读设置，初始化幂等；并发进入时复用同一个初始化过程，失败允许重试。
2. 背景与象限配置事件使用 `restartable()` 或保证唯一启动入口，继续用 `emit.forEach()`，避免自行增加手动订阅。
3. 移除重复初始化触发前验证它是否依赖标签到达；若有具体依赖，拆成明确的配置协调事件，不能直接丢掉必要更新。
4. 缓存主题，缓存键包含当前主题实际依赖的种子色、亮暗模式等配置。单次构建复用同一个主题结果。
5. 将根节点构建依赖限制在主题和语言等 UI 配置，用户、版本检查、下载进度通过各自监听处理；特别保留 AppHub 的用户 ID 和会员状态更新链路。
6. `setEnabledSystemUIMode` 移到必要的生命周期/模式变化处理，不在每次构建后重复发送。

### 验证与验收

重复触发初始化后每条设置流仍只有一个有效订阅。主题、语言、系统亮暗、背景、象限配置正常更新；用户资料和下载进度变化不会重复计算主题，AppHub 的身份与权益联动仍正常。

预期属于降低叠加开销，不能单独承诺解决十秒等待。风险低到中等，可较早独立交付。

## 10. 加载与异常：明确失败状态和加载提示归属

### 原因与代码位置

`TaskListBloc`、`RootTaskBloc` 的部分数据流先进入 loading，再 `emit.forEach()`，未设置本地错误状态。`TaskListBlocProvider` 与 `RootTaskPage` 又共同显示/关闭全局 EasyLoading，多个请求没有统一所有权。

### 修改方案

1. 为查询流显式处理错误并发出 failure，保留已有任务数据，提供重试入口；重试继续沿用当前事件与订阅结构。
2. 区分列表首次加载、后台数据变化、用户主动提交，后台刷新不遮挡已可交互的整个页面。
3. 第一版先补错误收尾和加载提示的请求标识/所有权，避免一个列表关闭另一个提交操作的加载提示。
4. 如采用局部占位，仅调整展示，不合并标签、空白拖放区、侧栏数据流。新用户可见错误文案加入全部 ARB 并生成本地化。
5. 页面销毁、取消请求和 BLoC 关闭后释放该页面拥有的提示，不影响其他页面。

### 验证与验收

数据库/平台异常、多个请求重叠、快速切换日期、页面退出后返回均不出现永久遮罩、提示相互关闭或数据清空。首次无数据和加载失败不能混为同一个状态。

这项改善「看起来卡住」及失败后的可恢复性，不直接减少 SQLite 或原生调度的执行时间。

## 启动编排补充：利用 Splash 动画并行准备

### 当前实现与目标

- `SplashPage` 的淡入、位移动画同时开始，配置时长约 500ms，不是两个相加后的 1 秒。
- `SplashCubit.onLaunched()` 已经并行发起会员查询，导航等待动画结束、会员结果以及 `AppBloc.isInitialized`。
- 数据库检查、Repository 构建和 `UsersRepository.initialize()` 位于 `bootstrap._initApp()`，在真正的 Splash 出现之前完成。资料没有缓存时可能等待网络，这段不能靠现有 Splash 动画覆盖。
- `AppBloc` 的用户监听可在 Splash 期间触发云同步；不能假设所有同步都到首页才开始，更不能再新增一轮相同同步。
- 重复实例生成、首页计数与列表订阅、首页提醒重排仍主要在首页挂载时触发。

目标是让启动视觉呈现和可复用的准备工作重叠，减少进入首页时同时启动的大量工作；同时缩减实际工作量、消除阻塞，不能仅把十秒等待转移到 Splash。

### 建议的三个阶段

**阶段一：必要启动与安全门控。**

保留隐私同意、必要 SDK 初始化、当前账号确定、数据库检查/迁移与安全打开的依赖顺序。正常业务读写必须等待安全开库。若希望这段也展示动画，先让最外层 `_BootstrapLoadingPage` 复用不依赖 Repository/BLoC 的启动动效，而不是把尚未构建的 Repository 塞进 `SplashCubit`。记录同一次动画的完成状态，避免 bootstrap 切换到 Splash 时再强制重播一遍。

数据库检查仍需按第 8 项移到独立 isolate；只提前显示动画但继续在 UI isolate 扫描数据库，动画同样会卡顿。资料与会员网络等待策略属于单独的产品行为决策：本方案先保留现有权限与付费路由，不默认把未知会员当成非会员。

**阶段二：动画期间执行可复用的本地准备。**

1. 复用第 9 项的设置初始化和主题结果，避免首页再次初始化相同设置。
2. 通过第 3 项的共享协调器提前执行当前账号、当天所需的实例生成。原有首页调用进入同一个进行中任务或已覆盖区间，不另做一遍；第一版保留现有三个月窗口，不能借编排顺便缩小范围。
3. 按测量需要预热数据库连接或小规模本地索引/映射；若首份查询只是预热却不能复用结果、也不能证明缓存收益，则不新增这次读取。
4. 首页任务与标签 Stream 保持现有创建位置，不在 Splash 隐藏挂载首页、不提前创建整套首页 BLoC、不额外建立各标签/空白拖放区/侧栏订阅。
5. 不直接调用带隐含同步副作用的 `getTaskCount()` 或 `getAllTags()` 作为预热接口；必要时新增职责明确的一次性本地准备接口，避免额外触发网络和关联维护。
6. 首次启动的示例数据有语言与首次状态依赖；需要前移时，单独设计幂等的本地种子数据准备，不能简单重复派发 `AppLaunched`，造成启动计数或样例数据重复。

**阶段三：非首屏维护可继续后台执行。**

优化后的提醒差量协调、组件刷新、云同步、版本检查等不作为进入首页的全部完成条件。是否在动画阶段启动或首屏绘制后启动，由 CPU、数据库队列和磁盘争用的测量决定；同一时间避免无上限并发。时间紧迫的有效提醒应优先处理，不能因等待首页进入而任意推迟。

第 1 项的固定 1,000 次取消、第 2 项的原生 `runBlocking` 必须先优化。把原实现原样搬到 Splash，仍可能阻塞动画，并让未完成任务继续争用首页资源。

### 任务生命周期与导航条件

- 建议在 composition root 注册应用级 `StartupPreparationCoordinator`（暂定名），向 Splash 提供已存在任务的状态，向 Repository 提供可复用的本地准备结果。页面退出不终止有效准备；账号变化或任务版本变化使过期结果失效。
- 按启动轮次、用户、日期和数据版本去重；重建 Splash 不重复发起工作。跨午夜、账号切换和同步修改规则都需重新核验。
- 动画完成、路由所需信息、必要安全初始化分别表示，不能继续用一个 success 状态混合表示全部阶段。
- 可选预热只利用动画已有时间。动画结束时已完成就直接进入；未完成则沿用同一个任务，首页按现有加载/错误状态继续接收结果，不再次发起独立任务，也不默认延长动画等待所有预热。
- 若某项准备是首屏正确性必需条件，需明确归类为必要门控，失败时给出重试或错误状态；不能把超时当空数据，也不能以任意超时跳过数据库恢复。
- 原付费页面出现频率、登录路由与会员判定策略先保持。将会员远程查询改为「缓存判定 + 后台刷新」另行确认并验证付费用户体验。
- `async`、`unawaited`、`Future.microtask` 只改变等待/调度方式，不等于新增执行线程。Dart 重计算走合适的 isolate；Android 插件内部阻塞需在 Kotlin 实现中处理，不能仅靠 Dart 包装解决。

### 与现有优化项的对应关系

- 第 1 项提醒：先修差量与迁移，再纳入统一维护队列；不让所有提醒完成成为 Splash 门控。
- 第 2 项组件：先后台执行及去重，再安排刷新时机；不要为首页准备而主动绘制所有组件。
- 第 3 项实例：最适合提前触发，但必须由现有首页入口复用同一生成状态。
- 第 5 项批量读取：继续优化每次查询本身；不能为预热额外复制一套首页数据流。
- 第 6 项同步：复用已有进行中请求，保持本地数据可先显示；不能在 Splash 再触发一次 force 同步。
- 第 7 项逾期统计：保持当前行为；时机调整仍按用户暂缓订阅改动的约束单独确认。
- 第 8 项完整性检查：现有 Splash 覆盖不到，需调整最外层启动展示或另行移动启动边界，同时保留安全开库顺序。
- 第 9、10 项：分别提供唯一初始化与明确的准备/加载/失败状态。

### 验收方式

同时记录图标点击到启动动效首帧、动画结束、首页首帧、首份正确本地列表及可交互时间；不能只报告「进入首页后快了」。动画帧时间也纳入对照。

验证预热先完成、动画先结束、离线、无缓存、准备失败、Splash 退出后完成、跨午夜及账号变化。确认首页订阅数量和筛选/拖拽业务不变，实例生成与同步执行次数没有增加。正常启动不额外添加固定等待时间。

## 业务影响与数据库变更边界

### 总体结论

方案的目标是保留业务规则，但不同优化会触及不同程度的业务正确性与显示时序，不能统一称为「不影响业务」。可以先实施一个不升级数据库的基础批次；完整的预约账本、持久化生成覆盖记录和索引方案需要本地 schema 迁移。

### 主要改变执行方式，预期业务结果不变

- 第 9 项：主题缓存、一次性初始化、设置流去重。需验证主题/语言/配置仍实时更新；此处不涉及暂缓的首页任务订阅调整。
- 第 5 项的批量标签读取：不改 schema，但必须保持用户过滤、软删除、linkedTagId、父链与排序语义，属于有结果等价要求的查询优化。
- 第 2 项第一步：小组件转后台与刷新合并。无需业务库结构变更，但组件展示可能稍后更新，需要防止旧结果覆盖新状态。
- 第 10 项：错误收尾与加载提示归属。无需业务库结构变更，会改变失败提示与遮罩交互，需要保持提交操作的正确阻塞行为。
- 第 3 项仅合并进行中的实例生成请求：可以先不改 schema；仍要验证规则变化时旧请求不会遮蔽必要的新一轮生成。

### 直接触及业务正确性或启动行为

- 第 1 项：提醒 ID、取消范围、调度顺序与旧预约迁移，关系到重复提醒、漏提醒和升级恢复。完整方案建议新增本地预约账本表，记录设备专属状态，不进入云同步。
- 第 3 项持久化覆盖范围：关系到任务是否显示、过期实例是否被重新生成。建议新增本地生成覆盖表，和实例更新放在同一 SQLite 事务中；首次迁移不能仅按现存实例的最大/最小日期推断中间区间全部覆盖。
- 第 6 项：增量同步与游标变更直接影响多设备一致性。游标按用户存入 SharedPreferences 可以不改 SQLite schema，但必须进行存储 key 迁移；关联增量若依赖服务端支持，可能需要 Supabase 触发器或独立增量接口，需核实后决定。
- 第 8 项：检查线程迁移不改 schema，但恢复与开库顺序涉及数据安全；降低检查频率、改变损坏恢复策略作为独立改动。
- 第 7 项延迟统计或聚合缓存：会影响计数更新时间，聚合正确性也需要独立验证。第一版仅优化现有查询；持久化聚合缓存可能需新增本地表，当前不安排。
- Splash 并行准备：复用同一任务且不改变导航等待条件时可以不改 schema；增加进入门槛、使用缓存替代会员判定、前移首次样例数据创建等属于独立的业务时序决策，不能默认包含。

### 哪些属于数据库升级

- **本地 SQLite 新表**：完整提醒预约账本、持久化实例生成覆盖记录。均为本地辅助状态，不要求在 Supabase 新增对应表，也不修改任务/笔记/标签业务字段。
- **本地 SQLite 新索引**：第 5、7 项根据查询计划选定后，通过 Drift 声明与迁移落地。虽然不改业务字段，仍是 schema 变更，需测量旧库首次创建耗时。
- **偏好存储迁移**：同步游标按用户归属、提醒迁移标志、可选组件去重状态。与数据库 schema 升级区分管理。
- **组件派生数据或快照格式**：第二阶段若采用专用组件数据，需要版本兼容与原子替换；这不等于修改主业务库结构。
- **服务端数据库**：目前没有确定必须执行的 Supabase schema 修改；只有增量完整性核查后，才决定是否需要服务端触发器/接口支持。

## Splash 复查记录（2026-10-17）

本轮复查只补充测试与记录，未修改生产代码。原有三个月窗口、唯一约束、忽略插入与整体事务仍能保护实例结果；现有测试未发现新增重复实例、时间偏移错误、单次删除标记复活或规则更新后被旧结果覆盖。以下性能问题仍需处理，不能因动画不等待准备完成而视为已经解决。

1. **生成期间占用共享连接的时间仍然过长。** 外层事务覆盖候选查询、每批 isolate 创建/计算/返回与全部写入，生产数据库默认未配置额外读取连接。因此普通首页查询也会等整个事务提交。分批不等于分批提交，而且每 32 个任务调用一次 `compute` 会创建一次短期 isolate；候选很多时额外启动开销也发生在事务占用期间。新增测试已复现查询排队。优先方案是事务外计算快照，短事务重新核对主任务规则、时间、删除/分离状态后写入；不匹配的结果丢弃或重算，不能简单去掉事务保护。计算端考虑复用 worker，同时保持批量与内存上限。
2. **当天不执行的系列会额外展开。** 当前候选 SQL 仅以当天是否存在有效实例判定，Splash 完成后移除进行中状态，首页再次调用时仍会选中明天执行的周任务。新增测试复现两次展开/写入批次，最终实例 ID 集合保持一致：没有数据重复，但增加计算和忽略插入开销。需要支持经过有效性校验的准备结果复用；不能直接以日期成功标记跳过后续生成，避免漏掉新任务、规则变化和实例删除。
3. **与既有强制同步叠加时仍可能回到 UI 线程计算。** AppBloc 在收到初始用户身份时调用 `syncTasks(force: true)`；当远端返回晚于准备完成，`insertOrUpdate(refreshOccurrences: true)` 会重建刚预热的缓存，`_refreshCachedTaskOccurrences` 仍直接同步调用规则计算。即使规则不变也会重建。新增测试复现空缓存时强制更新不生成、准备填充后相同强制更新再次生成的差异。该条件取决于网络返回顺序；源代码与数据层测试能证明重复工作路径，实际掉帧幅度仍需设备测量。可保持既有同步策略，将这条缓存重建计算也移到后台，并维持当前数据正确性约束。

建议按共享连接等待、准备结果可靠复用、缓存重建后台化的顺序处理。无需改变首页订阅或数据库结构，但每项都需要并发与失效校验，不能用直接解除事务、缩减三个月范围或永久缓存成功状态替代。

复查验证：包含前三个新增复现用例的完整回归集合共 272 项通过；随后补充的强制缓存刷新用例与该测试文件全部 13 项通过。本轮共新增 4 项针对性测试，9 个相关文件静态检查通过，最后补充用例的文件再次检查通过。未进行红米真机耗时和掉帧测量。

## Splash 三项问题修复记录（2026-10-17）

### 长事务与数据校验

- 预生成不再创建覆盖整段计算的外层事务。候选查询和每批规则计算在自身写事务之外执行；每批最多 32 个主任务，写入时才开启短事务。
- 短事务重新读取主任务，核对重复规则、起止/截止时间以及删除、父子和分离状态。旧结果不匹配则丢弃；仍符合生成条件的任务按最新快照重算，已删除或已不符合条件的任务不写入。
- 提交前读取原实例表，含已删除实例，仅补缺失的日期，不覆盖单次删除或分离留下的隐藏标记。
- 每轮完成后再扫描尚未处理的新任务/规则。计算期间的合并请求会要求再次检查，避免创建任务时复用进行中的 Future 后漏生成。不同事务调用上下文仍分别执行，不等待排在外层事务之后的请求。
- 生成窗口仍为三个月。提交原子性改为每批缓存；一次批次失败时已提交的有效批次保留，失败批次回滚。整个准备 Future 仍返回失败，重试通过实际数据库行补齐，不依赖“完成”标记。首页 Stream 会随缓存分批到达更新；任务和活动等业务写入的原事务边界不变。

### 可靠复用与内存边界

- 新增 `TaskOccurrenceGenerator`，缓存仅保存规则与日期展开的纯结果。键包含主任务 ID、规则、全部相关时间、查询窗口和本地日历/时区信息；规则、日期或时区变化均不能命中旧结果。
- 日期摘要只记预期日期的整数时间戳，最多 1024 个键、65536 个日期。完整实例对象缓存最多 128 个键、1024 行，采用最近使用顺序淘汰，避免为了预热长期持有大量 Jiffy 对象。
- 摘要命中仍核对现有实例表的每个日期（包括隐藏标记），全部存在才跳过展开与写入；实例表清理或缺行时仍补齐。摘要不是数据库覆盖状态，不需要新增订阅、表、列或失效标记。
- 已结束或当天不执行的系列也能复用空结果/日期摘要；完整实例对象淘汰后，摘要仍可避免重复计算。超出容量的摘要被淘汰后安全退回正常计算，不影响数据结果。
- 仅对每日规则复用包含窗口的子结果，其他频率保持原计算器的窗口语义，避免借优化改变周规则等既有行为。

### 后台计算与错误收尾

- 多个 API 共用一个串行计算 worker，每批复用该 isolate，不再每 32 个任务创建一次。worker 空闲 10 秒退出，下次需要时重新启动；计算失败会完成当前 Future，后续请求仍可继续。worker 不持有数据库连接或插件对象。
- `_refreshCachedTaskOccurrences` 也使用同一后台计算入口，保持原缓存日期范围与隐藏标记保护。强制同步仍执行原有刷新语义，没有改为增量或跳过强制修复。
- 保留既有同步/调用者外层事务。缓存重建若在该事务内调用，仍可能等待后台计算并占用该事务；本批解决预生成自身的长事务和两条计算路径的 UI 线程重计算，不声称消除了既有整批同步的数据库等待。
- 创建/编辑后不等待的实例生成独立记录失败，避免数据库已关闭等后台失败成为未处理异常；显式等待 `preGenerateTaskOccurrences` 的调用仍收到原错误，Splash 协调器也仍按失败收尾。

### 验证

- 完整回归集合 288 项通过；12 个相关源码/测试文件静态检查通过，`git diff --check` 通过。
- 新增/改写的针对测试验证：计算暂停时首页查询可完成；期间规则更新无需等待且旧计算不能写回；删除/子任务/分离/移至未来/取消规则时不插入旧实例；新到达系列补齐；单次隐藏标记在提交前后均保留；分批失败后补齐；实例表清空后恢复；对象缓存淘汰后复用摘要；强制刷新与预生成共用 worker 无互等。

## 数据库完整性检查后台迁移记录（2026-10-17）

### 已实施

1. `AppDatabase.recoverCorruptIfNeeded()` 在主 isolate 完成 Android 旧版 SQLite 动态库兼容处理、临时目录及 App Group/文档目录解析，将数据库路径与临时目录两个字符串交给后台检查流程。恢复所需的 SQLite 临时目录配置在工作 isolate 中明确执行，不在工作 isolate 调用平台通道。
2. 通过 `compute` 在独立 isolate 执行整个同步恢复流程：文件存在性检查、打开 SQLite、`PRAGMA quick_check`、关闭连接、必要时删除 WAL/SHM、复查及隔离主库。可在 profile 中识别 `database-integrity-check` isolate。
3. `bootstrap` 仍 await 检查/恢复结束，随后才执行路径迁移检查、构建正式数据库和 Repository；没有新增超时跳过检查，也没有把真正的恢复操作留在后台继续运行后提前开库。
4. 检查调度器合并同一文件的进行中请求，并串行处理文件检查，避免检查/恢复之间竞争和并行修改 SQLite 临时目录原生状态。任务失败向原调用者传播，同时释放请求记录；后续队列和重试仍能执行。完成后不缓存检查结果，各次启动仍检查。

### 保留的行为

- 正常库不进入恢复清理；首次安装无数据库时不创建文件。
- 保留原来的损坏判定：SQLite 错误码 11/26 或原有 malformed/CORRUPT 文本判断；busy/locked 等非损坏错误仍按原逻辑跳过恢复，不隔离完好的数据库。
- 确认损坏后先清理 WAL/SHM 并复查，仍失败才进入 `.corrupt` 隔离；已有备份替换、重命名失败时删除原文件的回退行为保持原样。本轮没有调整文件保留策略或恢复协议。
- 每个检查连接仍由 `finally` 关闭，恢复异常仍传播；业务库只在整个 Future 完成后进入原启动链路。
- 数据库 schema 保持 3，首页订阅、重复实例业务、提醒迁移和同步策略没有改动。

## 数据库完整性检查复查记录（2026-10-17）

本轮仅新增两项针对性测试与审查记录，没有修改生产恢复策略。后台迁移与旧实现逐分支比对，未发现新增的损坏分类或启动等待错误；但不能据此承诺不丢数据，旧的破坏性恢复流程仍存在以下风险。

1. **部分页面损坏不代表 WAL 中的数据都不可恢复。** 新增真实 SQLite 夹具：一张表的主库页面损坏，另一张表的未同步 Outbox 记录仍可从 WAL 读取，同时保留一个只读事务模拟共享库读者。后台恢复确认损坏后删除 WAL/SHM；复查报 `SQLITE_IOERR_VNODE`（扩展码 6922，主码 10）被旧逻辑视为“跳过恢复”。释放读连接并重新开库后，原先可读的 Outbox 记录已经不存在。该结果证明旧策略可丢失待同步数据，并可能在恢复未成功的情况下继续启动。该复现采用桌面 SQLite 临时库，未在 iOS 小组件真机复现。
2. **隔离并不保证保留原始文件。** `.corrupt` 使用固定名称，旧备份在新隔离成功前删除；新隔离重命名失败时又直接删除原主库。已有针对性测试证实重命名失败分支会删除主库。该风险来自原策略，不是本次线程迁移新增。

并发与开库边界：当前生产代码只有 `bootstrap._initApp` 调用恢复，且严格 await 整个检查/恢复 Future，之后才执行路径迁移并创建正式 `AppDatabase`。worker 同步执行完整流程，检查连接始终在 `finally` 中关闭；没有超时放行或恢复尚未完成就通知成功。调度器合并同一规范化路径的进行中请求并串行检查不同文件，失败不会阻断后续请求。但它仅保护当前 Dart isolate 内的恢复请求，不覆盖所有数据库连接或其他进程；iOS 的 `WidgetDatabase` 独立打开 App Group 共享库，不受该 Future 门控。这是现存共享库边界，不能以调度器串行化替代文件访问协调。

验证：数据库恢复专项共 13 项通过，包括新增正常 WAL 写事务期间检查（提交后的记录保留）与上述真实数据丢失复现。busy/locked 不进入隔离，正常库与正常 WAL 不触发清理。测试通过表示已验证当前行为，其中包含风险复现，不表示风险已经修复。

建议后续优先调整损坏恢复的文件保留策略：在共享访问不能协调时停止破坏性清理；恢复前保留完整主库与 sidecar；备份使用唯一名称且保留失败现场；重命名失败向上传递错误而非删除主库。需要区分“检查正常”和“检查因 I/O/锁等原因未完成”，尤其恢复已开始后不能把跳过复查当作恢复成功。这些修复不要求修改数据库结构、首页订阅、提醒迁移或同步策略，但会改变原文件恢复策略，需作为独立修复处理。

## 数据库恢复文件保全修复（2026-10-17）

本节覆盖前两节中的旧恢复行为，按用户授权修复 WAL 清理与隔离失败删除主库的风险。数据库结构、首页订阅、提醒迁移及同步策略均保持不变。

### 当前行为

- 完整性检查继续在后台 isolate 执行，SQLite 改用 `OpenMode.readOnly`，不再以读写模式打开原库进行启动检查。正常库直接放行；主库和日志都不存在时仍按首次安装继续。
- 移除删除 WAL/SHM、覆盖 `.corrupt`、重命名原库以及失败后删除主库的全部恢复分支。确认损坏后只复制文件，原主库和所有日志保留在原路径，旧备份不变。
- 每次损坏保全使用 `planbook.sqlite.recovery/attempt-*` 唯一目录，复制主库与当时存在的 `-wal`、`-shm`、`-journal`，逐文件 flush。复制完成后才写 `manifest.json`，记录文件清单、`copyCompleted: true` 与 `consistentSnapshot: false`。部分失败保留已复制文件，没有完成标记，并传播异常。
- 这些文件是诊断及后续恢复用的原始拷贝，其他进程仍可能写入，不能将其视为一致性快照或自动恢复成功。即使复制全部完成，也始终抛出 `DatabaseRecoveryException`，不放行损坏库或创建空库。
- SQLite busy/locked/I/O 等非损坏错误不再返回成功，而是作为“检查未完成”抛出异常；普通异常文本里出现 malformed/CORRUPT 不再被猜测为损坏。只有 SQLite 损坏码或 quick_check 返回的实际错误结果进入保全。
- 主库缺失但仍有 WAL/SHM/rollback journal 时停止启动，避免误当首次安装；数据库路径不是普通文件时同样停止。备份目录被占用、复制失败或检查中断均保留原文件并传播错误。
- `bootstrap` 保持先 await 检查、再执行既有路径检查、最后创建业务 `AppDatabase` 的顺序。检查/保全异常不会触发同步时间戳清理、Repository 创建或同步引擎启动。

### 验证与使用影响

- 恢复专项 18 项通过。原数据丢失夹具现在验证：另一读连接持有损坏库时，主库与 WAL 原始字节保留，SHM 存在，完整备份保留相应文件，重新开库仍能读取原 Outbox 记录；失败 Future 后的业务开库回调不执行。
- 启动、planbook_api、database_planbook_api 与 TasksRepository 完整回归共 306 项通过；恢复源码、专项测试和 bootstrap 三个文件静态检查通过，`git diff --check` 通过。
- 覆盖正常库、正常 WAL 写事务、真实独占锁 busy、唯一备份重复保全、旧隔离路径被目录占用、备份根路径被文件占用、部分复制失败、I/O 异常、主库缺失但 WAL 仍在、符号链接拒绝及恢复调度队列的失败重试。
- 检查不能完成或确认损坏时，应用会停止在启动阶段，不再自动删除现场并启动空库。这是本轮保护未同步数据的明确行为变化；数据修复与可视化错误处理不在本轮实现范围。
- 不自动清理保全备份；反复启动同一损坏库会产生多份保全文件。磁盘空间不足导致复制失败时仍保留原库并停止启动，不能靠删除原文件来腾空间或继续运行。

## 提醒重排与启动强制同步优化（2026-10-18）

本轮已获用户明确授权优化这两项。下面记录当前实现，覆盖前文“后续单独确认”的旧状态。业务数据库 schema 仍为 3；没有新增表、列或索引，没有合并首页任务订阅。

### 提醒调度与旧预约迁移

- 由 bootstrap 注入权威本地任务读取和当前账号。全量校正覆盖带提醒的单次、重复任务，已完成的单次任务不重建，已删除、移除提醒或取消日期的任务由期望集合差量移除。单次删除实例与重复实例完成等业务范围沿用原语义，不在本轮重新定义。
- 初始化共享 Future，失败后允许重试。统一串行队列保证设备账本和原生预约只有一个写者；同任务待执行请求合并为最新意图，运行中的旧请求结束后再执行新请求。启动、前台恢复、同步完成和任务动作均使用此入口；换号/注销触发全量校正，旧账号在后续原生操作前失效。
- 设备预约账本保存到 application support 的 `task_alarm_reservations_v1.json`，不进入业务库或 Outbox。先 flush 临时文件，再同目录原子替换；文件内容的 JSON 编解码移至计算 isolate。账本损坏或版本未知时停止本次校正，不通过清空通知掩盖问题。
- 业务键采用账号、任务 ID、实例实际日期、完整提醒配置及重复配置序号。通知 ID 持久化分配，检查账本、系统 pending 与 active ID，避免旧的 Object.hash 跨启动变化及下标漂移；Android 5.x 无 active 查询能力时保留账本/pending 碰撞检查。
- 每批共享系统预约列表，先取消失效项，再新增/更新变化项，一致项不执行原生操作；不再固定遍历每任务 1000 个取消 ID。原生变更后再次核对 pending/payload，静默丢弃预约或取消失败不能标为成功。已到触发时间的预约不因核对期间触发而反复重建。
- 升级先持久化 `clearing`，再调用仅清理待触发预约的接口，保留已展示通知；清理后保存 `building`，按权威本地任务补齐。重建全部通过系统核对后保存 `complete`。清理中断可重试；进入 building 后重试不再次清空已成功的新预约。原生成功与账本最终保存之间中断，通过预先持久化的 ID/意图和系统 payload 校正。
- 原提醒范围保持未来 60 天、最多 50 个实例。规则展开与提醒计划构建在独立 isolate 中完成，不持有数据库事务。迁移与预约失败记录日志并保留重试状态，不抛给原有 unawaited 调用形成未处理异常；下次启动、前台恢复或任务请求继续校正。
- 旧版本迁移有清理至重建的空窗；首次大量旧预约清理仍取决于通知插件的原生实现。没有调整平台通知容量上限或预约范围；系统静默限制时会检测到缺失并保留未完成状态，不能据单元测试保证真机全部提醒可预约。

### 启动同步与数据库占用

- 任务与笔记分别按账号合并整个“下载—合并—游标保存”Future。普通请求等待进行中的强制同步；强制请求遇到普通同步则排队一次，后续请求复用排队结果。成功后普通请求才进行 3 秒节流；失败立即允许重试，force 不受节流吞并。移除远端 API 的“3 秒内返回空列表”行为。
- 任务规则计算和缓存快照读取在写事务外进行；提交时重新校验本地任务完整快照、实例表与 Outbox。快照变化时重算，最多重试 8 次；持续冲突返回失败并保留游标。使用序列化字段比较完整任务，避免 Drift 列表字段按对象身份比较造成无限重试。
- 每个任务及其标签、活动、分离压制、实例变更使用短事务原子提交。强制同步仍校验旧缓存；有效实例的日期与起止/截止值均正确时，不删除重写实例。隐藏标记仍保留；错误缓存仍修复。笔记及关联同样按单条笔记提交。

## 启动增量同步落地（2026-10-18，接续上一轮）

本节取代上节“当前仍保留启动 force: true”的阶段状态。数据库 schemaVersion 仍为 3，不新增表、字段、索引或服务端触发器；首页各标签、空白拖放区、侧栏的订阅数量及组装方式不变。

### 关联链路核查与协议选择

- 现有完成/撤销操作可只改 `task_activities`，任务标签和笔记标签也会独立替换，主表时间没有可靠的联动保证。旧客户端离线 Outbox 还会上传早于当前游标的时间，部分正文更新没有更新 `updated_at`。仅改成父表时间过滤会永久漏数据。
- 因此采用“按账号分页读取 `id + xmin` 轻量版本清单，只下载新增或版本变化记录正文”的客户端增量对账。任务、笔记、标签、任务活动、任务标签、笔记标签各自对账，去掉依赖嵌套关联展开的拉取协议，避免嵌套关系行数上限。笔记引用的任务由任务同步链路负责，启动协调同时请求任务和笔记。
- `xmin` 使用 PostgreSQL 现有系统列，无需修改数据库结构。它只作不透明的相等性标记，不比较大小，也不作为最大事务号水位。[PostgreSQL 系统列说明](https://www.postgresql.org/docs/15/ddl-system-columns.html)说明它标识行版本的创建事务，同时提醒事务号会回绕；本方案不将它当作永久唯一 ID。客户端版本清单是可重建缓存，主动强刷始终下载完整正文。
- 这不是网络开销与变化数严格成正比的服务端日志增量：每轮仍扫描完整轻量清单，正文下载与本地写入才按变化收敛。数据规模很大时，后续若要连清单扫描也去掉，需要单独设计服务端可恢复变更日志协议。

### 分页与确认边界

- 按 `user_id` 显式隔离，`id ASC` 与 `id > lastId` 配套；每页最多 200 条。短页不作为结束条件，直到服务端返回空页，防止服务器行数上限低于请求值时截断。重复/缺失主键直接失败，不提交完整清单。
- 正文按最多 100 个主键分批，正文同样分页至空页。保存实际合并正文携带的版本，而非较早清单的版本；清单后发生的变化可以下一轮继续发现。
- 每轮从清单头开始，不推进全局时间/事务号水位。分页期间插入到已扫描区间的记录，下一轮能补到；跨表、跨页不宣称拥有同一个数据库事务快照。
- 版本清单按业务库代次、账号、表隔离，仅确认成功提交到本地的记录。Outbox 跳过项不确认版本；部分事务失败可以重放。业务库缺失时先轮换代次并清理旧缓存；较大清单的 JSON 编解码放到计算 isolate。
- 旧接口会物理删除标签关联。对完整清单中缺失的本地有效关联，再按 ID 向服务端核实；仍缺失才在本地打软删除标记，不物理删本地记录。父任务/笔记、关联本身及标签的待上传修改均受保护；清单或二次核实失败不执行删除。
- 任务、笔记和标签的完整拉取到提交过程在同一业务库内排队，避免共享标签的旧快照后写入。数据库查询不加入该同步队列，关联每批 200 条用短事务提交。
- 拉取开始时的待上传记录，以及拉取期间新增的 Outbox 记录，本轮始终受保护。即使并发上传已将其标记成功，也不能被先发出的旧远端响应覆盖。分页每次请求前后检查账号，换号及时停止旧请求。

### 旧实例修复与启动模式

- 旧实例修复在本地独立执行，按账号、业务库代次和修复版本记录完成标记；离线也可先完成。失败不写完成标记，下次重试。主动强刷仍独立核验本地缓存，不再通过“拉全量远端任务”来触发修复。
- 计算在写事务外，短事务重新检查任务与实例快照；期间规则变化则重新读取本地权威任务重算。只更新实例缓存，不写回旧任务；本地有 Outbox 的任务也可以安全修缓存。已取消规则或删除的任务清理有效缓存，单次删除/分离实例的隐藏标记继续保留。
- 同账号且上次启动同步已成功时，普通冷启动使用 `force: false`。首次登录、换号、注销后重登与主动强刷继续全量。首次升级没有新版版本清单时需要建立一次基线，之后正文走增量。
- 账号完成标记等任务、笔记、标签全部成功后保存，旧账号晚返回不能覆盖新账号标记；注销同时清空 AppState 用户，避免下一次账号判断沿用旧用户。后台同步失败记录日志并保留基线，不影响本地页面读取。

## 日视图列表切换日期卡顿（2026-10-18）

用户补充确认发生在日视图任务列表；断网表现和红米机型/退出日志仍未知。本轮处理该路径的底层冗余计算与组装，不改变首页分组、空白拖放区和侧栏的订阅，也不升级数据库结构。

### 已确认的执行链路

- `TaskTodayBloc` 切天后重订日期计数、当日目标/总结；各标签和空白区仍按原监听分别重新请求日任务。列表和计数入口都会请求实例准备，同日进行中请求继续复用。
- 周/月/年重复任务在所选日期没有有效实例时会成为候选；原纯计算缓存以精确日期窗口为 key，切到邻日会因窗口变化重新展开三个月，即使绝大多数日期已经计算并写入。
- 日查询会 JOIN 标签、活动、实例、子任务与子任务活动；存在多条关联时，结果行会放大。原实体组装逐行复制父任务与子任务列表，并线性查找已加入的子任务，进一步放大主 isolate 的组装成本。
- 日视图最外层 Builder 原先也响应 `taskCounts`，计数到达会让不依赖该字段的日历、列表布局再次构建。`getTaskCount()` 同时会触发后台普通增量同步；本轮保留其刷新时机，不擅自降低远端数据发现频率。

### 已实施

1. 任务结果按任务/子任务主键临时组装，最后一次性构建父实体。保持父任务首次出现顺序、实例/父活动最后非空项、子任务首次出现项及其活动的原选择口径，不跨查询缓存业务实体。
2. 日查询中仅用于筛选的 `task_tags` JOIN 使用 `useColumns: false`，保留 JOIN、WHERE 和原 Stream，只减少返回/解码的标签关联字段。标签仍通过原批量 API 组装；没有通过删除 JOIN 改变结果行或计数口径。
3. 对逐日判定、与窗口起点无关的规则（明确指定星期的周规则、月规则、年规则），纯计算缓存按月边界对齐，使邻日三个月窗口可复用同一结果和日期摘要。返回与写库始终裁剪回原请求范围；缓存命中仍核对数据库实际日期，缺行照常补齐，隐藏标记不复活。
4. 未指定星期的周规则仍按原精确窗口计算；每日规则保留原复用方式。规则、任务时间、结束条件与时区仍参与缓存键。有界实例缓存和轻量日期摘要预算不变，分组失败也会限制已产生的纯缓存容量。
5. 日视图外层 Builder 排除仅计数变化的重建，日期、日历格式、目标与总结仍正常更新；各数据订阅不增减。首次纯计算可能比业务窗口略宽，成本放在 worker，换取后续切天复用；不额外写入未来范围，仍需在真机同时观察首次准备开销。

### 验证与限制

- 新增真实 SQLite 用例覆盖切天前后的标签、完成状态、子任务、账号过滤，以及原 Stream 在子任务修改后的实时更新；分离实例按实际日期归日的回归继续通过。
- 指定星期的隔周、隔月指定日/次数、每月最后一个周五、默认月/年规则、指定年日期及明确结束时间，均逐个与原计算器的原始请求窗口比较。覆盖向前/向后切日、跨月、规则/时间修改及混合规则返回顺序；数据库用例验证连续切天不重复计算、缺行补齐、隐藏行保留、不新增 Outbox、不扩大三个月写库范围。
- 同一批 7,728 行关联结果的桌面组装对照：旧实现五次约 32.8/23.8/19.4/19.9/12.0ms，新实现约 21.3/9.2/6.3/5.7/4.7ms。中位数约 19.9ms→6.3ms，**只计实体组装及其标签读取，不包含前置 SQL 查询、结果解码、布局绘制，也不代表红米整页切换耗时**。未把机器相关时间阈值写成测试断言。
- 完整回归 438 项通过；本轮 8 个源码/测试文件静态检查均无诊断，`git diff --check` 通过。
- 尚未取得红米真机的切天 trace，不能宣称用户卡顿已完全消除。复杂 JOIN 的结果行放大、快速切天留下的进行中工作、计数读取触发后台增量同步、多个分组共用加载提示仍是后续候选，需要分段测量后继续处理；本轮未改变这些业务和交互时序。

## 切天优化安全复查（2026-10-19）

用户要求核查重复计算与标签筛选的业务影响。本轮复现并修复了一个真实的夏令时边界，未把原常规日期测试通过等同于所有时区都安全。

- **已复现的问题**：当前 Jiffy 的日期推进使用固定 24 小时，日/周差也基于时间差。纽约 2026-03-09 附近的隔周任务，按月边界扩大的窗口与原请求窗口输出不同重复日期。秋季时差切换和每日规则截取旧窗口也须保护。该问题来自缓存窗口复用，不是标签字段优化。
- **修复**：扩大纯缓存窗口前检查所有日历日的午夜和时差，只有恒定时差窗口才允许复用；跨夏令时、午夜异常和过长范围回退原精确窗口。每日规则从旧大窗口截取时也核对旧窗口时差。检查按生成批次、日期摘要查询批次共享，不逐任务重复扫描。原规则计算器和三个月写库范围不改，缺行核验、规则版本核验及隐藏标记保护不改。
- **标签核查**：`useColumns: false` 仅减少主查询 SELECT 的标签关联列，不移除 JOIN、标签 ID/软删除过滤或 watched table。展示所需标签仍由批量查询补齐。新增真实 SQLite 流测试验证移除标签后任务离开标签组、进入无标签组，恢复标签后重新回到原组且标签实体完整；未删除首页订阅。
- **补充验证**：新增闰日、月末、跨年对照测试；通过独立 `TZ=America/New_York` 测试进程验证春季/秋季隔周与每日缓存共 4 个夏令时用例，不修改系统时区。原窗口在夏令时下自身的规则语义不在本轮改写，本轮保证优化不再引入额外偏差。
